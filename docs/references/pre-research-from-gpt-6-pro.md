这个需求有成熟的算法和产品实现可以借鉴，而且按照你给出的情况——**约 100 多个池子，同一交易对的流动性分散在不同协议**——我认为很适合做一个针对 Mantle 优化的 Router。

但这里真正要解决的，并不只是“找出更多路径”，而是：

> **在不同交易量下，联合决定经过哪些池子、每个池子分配多少交易量，以及这些交易如何组合执行，最终最大化扣除交易成本后的输出。**

我的建议是采用一套组合方案：

**有限跳数的路径搜索 + 基于边际价格的拆单优化 + 共享池的统一流量计算 + 完整交易模拟。**

其中，最值得借鉴的公开实现是 **Uniswap Smart Order Router、Balancer SOR、Sushi Tines**；更完整的数学建模可以参考 **CFMM 最优路由论文及 CFMMRouter.jl**。产品能力上，**1inch Pathfinder、0x/Matcha、Odos、KyberSwap、Jupiter Metis** 都有相关实现，但它们公开的算法细节和可复用代码范围差异很大。:chatgpt-content-reference{index="0"}

以下按你提供的“100 多个池子”作为设计前提；数值例子是构造算例，不是 Mantle 实时报价或回测结果。

# 一、首先把“多跳”和“拆单”分成三个层次

这里讨论的拆单，是**在同一笔原子交易中分配到多个流动性来源**，不是把大单分成多笔、在不同时间执行的 TWAP。

## 1.1 多跳：解决“经过哪些资产和池子”

例如，用户希望把 A 换成 B：

```text
直接交易：
A → B

两跳：
A → C → B

三跳：
A → C → D → B
```

即使存在 A/B 池，也不能直接断定它最好；经过其他资产的路径，可能具有更深的流动性，足以抵消额外手续费和 Gas。

Uniswap 的公开实现就是先在候选池中递归枚举路径，并用最大跳数、已访问代币和已使用池子等条件限制搜索。:chatgpt-content-reference{index="1"}

## 1.2 拆单：解决“每条路径分配多少输入”

例如：

```text
总输入 100,000 A

60,000 A → 协议甲的 A/B 池 → B
40,000 A → 协议乙的 A/B 池 → B
```

也可以拆到不同的多跳路径：

```text
60,000 A → C → B
40,000 A → D → B
```

**拆分比例不是由 TVL 比例、当前价格排名或者平均分配直接决定的，而是由完整报价曲线决定的。**

## 1.3 拆分后再合并：解决“多条路径共享中间流动性”

更完整的结构是：

```text
                 → 协议甲 A/C 池 ─┐
输入 A → 拆分                     ├→ 合并 C → C/B 池 → 输出 B
                 → 协议乙 A/C 池 ─┘
```

这时，交易结果不再适合简单表示为几条互不相关的路径，而更适合表示为一个**有向无环执行图，简称 DAG**。

1inch 在 2025 年公布的 Pathfinder 升级中，就明确介绍了把不同路径产生的中间代币合并，再执行共同后续步骤的做法。它优化的不只是拆单比例，还包括交易结构本身。:chatgpt-content-reference{index="2"}

**对你们而言，第三层非常重要：同交易对多池，加上少数核心中间资产，很容易产生共享前缀或共享后缀的路径。**

# 二、数学上，这不是普通的最短路径问题

## 2.1 每条“边”是一条随交易量变化的报价曲线

把代币看成节点，把池子中的兑换方向看成边，可以得到一个多重图。

但池子不能只记录一个固定汇率。它至少需要提供：

\[
y=f_e(x)
\]

其中，\(x\) 是输入数量，\(y\) 是输出数量，\(e\) 表示某个池子的某个交易方向。

以固定手续费的恒定乘积池为例：

\[
f(x)=\frac{Y\gamma x}{X+\gamma x}
\]

这里，\(X,Y\) 是池子的输入、输出资产储备，\(\gamma=1-\text{手续费率}\)。

由这个公式可以直接看出：输入增加后，后续每一单位输入能够换到的输出会减少。

因此：

> **小额交易的最佳路径，不一定是大额交易的最佳路径；整笔交易的最佳单路径，也不一定适合承担拆单中的某一小部分。**

集中流动性池还需要考虑不同价格区间的流动性变化，不能只根据总 TVL 或当前价格来推算大额交易结果。Uniswap 的官方说明明确区分了活跃流动性和价格区间之外的流动性。:chatgpt-content-reference{index="3"}

## 2.2 “最佳报价”应该怎样定义

建议第一版以 Exact Input 为主，也就是固定输入 \(Q\)，最大化净输出：

\[
\max \left[
\text{最终输出数量}
-
\text{折算为输出资产的交易成本}
\right]
\]

这里需要区分三个概念：

| 项目 | 如何处理 |
|---|---|
| 池子手续费、交易自身产生的价格冲击 | 应已经包含在 \(f_e(x)\) 中，不能重复扣减 |
| Gas、额外执行费用、聚合器费用 | 按实际收费方式计入比较 |
| 报价后到执行前的价格变化 | 属于状态变化和执行风险，不等于前面的价格冲击 |

Uniswap SOR 会比较 Gas 调整后的报价；0x 的产品说明也强调，优化目标应包含 Gas、税费和实际执行质量，而不只是展示出来的输出数字。:chatgpt-content-reference{index="4"}

另外，**Gas 折算后的净输出是经济比较指标，不应直接混同于合约的 `amountOutMinimum`**。如果 Gas 由用户另行支付，合约保护的仍然应是用户实际收到的代币数量。

# 三、有哪些算法值得借鉴？

我建议把算法分成六类。它们不是互斥选项，实际 Router 往往需要组合使用。

| 算法类别 | 主要解决的问题 | 最适合放在哪一层 |
|---|---|---|
| 有限跳数 DFS / 候选路径搜索 | 找到值得报价的多跳路径 | 第一层：路径发现 |
| 离散采样 + 动态规划或组合搜索 | 搜索路径组合和近似拆分比例 | 第二层：初始解 |
| 边际价格均衡 / 连续优化 | 精细优化拆单比例 | 第二层：比例精修 |
| 增量流量分配 | 边搜索、边拆单，并维护共享池流量 | 增强型路由引擎 |
| CFMM 凸优化与对偶分解 | 从整个池子网络联合求解 | 全图求解、离线基准 |
| 分段线性近似 + LP / MILP | 处理深度分段、容量及离散选择 | 特定池型和混合流动性 |

下面分别展开。

## 3.1 有限跳数 DFS：多跳搜索最直接的起点

### 工作方式

从输入代币开始，沿可兑换的池子向外扩展，直到到达目标代币，或者触及最大跳数。

例如：

```text
输入 A，输出 B

先找所有 A/B 池
再找所有 A/C/B 路径
再找所有 A/C/D/B 路径
```

对于你们的场景，我建议**从最多三跳开始评估**，而不是一开始允许任意长度路径。

这里的“三跳”是建议的初始搜索预算，不是已经验证过的最优参数。

### 为什么不直接用 Dijkstra？

普通最短路径算法需要相对固定的边权；AMM 的兑换效果却依赖交易量，还可能受到前面已经分配到同一个池子的流量影响。

把边权设为：

\[
-\log(\text{当前汇率})
\]

最多只能近似解决某种小额、静态汇率场景，不能直接解决大额交易、价格冲击、拆单和共享流动性问题。并且这种边权可能为负，也不能未经处理就套用普通 Dijkstra。

**因此，最短路径算法更适合作为候选生成或启发式的一部分，而不是整个 Router。**

### 可以借鉴谁？

Uniswap 的 `compute-all-routes.ts` 很值得直接阅读：它提供了一个清楚的有限跳数、避免重复访问的路径枚举框架。:chatgpt-content-reference{index="5"}

### 对 Mantle 的建议

不要仅按 TVL 保留每个交易对最大的一个池子。建议维护完整池图，再按具体交易请求筛选候选。

候选路径还应在多个交易规模上评估。否则，一条承接全量时表现一般、但承接 10% 输入时非常有竞争力的路径，会在拆单之前被误删。

## 3.2 离散采样 + 动态规划 / 组合搜索：最容易工程化的拆单方案

### 工作方式

把总输入分成若干份。

例如，以 5% 为一个单位：

```text
5%、10%、15%……100%
```

对每条候选路径计算这些输入规模对应的输出，再寻找比例相加为 100% 的组合。

例如：

```text
路径一 55%
路径二 30%
路径三 15%
```

### 动态规划可以怎么写？

假设路径互不共享池子，将总量分为 \(M\) 份，每份 \(\Delta=Q/M\)。

令 \(F_i(x)\) 表示第 \(i\) 条路径输入 \(x\) 时的输出。一个简化的递推是：

\[
DP[i,k]
=
\max_{0\le q\le k}
\left[
DP[i-1,k-q]+F_i(q\Delta)-C_i(q\Delta)
\right]
\]

其中 \(C_i\) 是对应执行成本，未启用路径时应为零。

这个基础版本的计算复杂度约为：

\[
O(KM^2)
\]

\(K\) 是候选路径数量。还可以增加“已使用路径数”维度，限制最大拆分数。

**但这个简单递推依赖路径之间相互独立。**如果它们共享池子，就需要加入冲突信息、共享流量状态，或者换一种模型。

### Uniswap 实际采用什么？

需要准确区分：我核查的 Uniswap `best-swap-route.ts` 采用的是**按比例报价之后的 BFS 组合搜索，并带有启发式剪枝**，不能简单说成一个严格的动态规划求解器。其代码还明确禁止不同拆分路径重复使用同一个池子。:chatgpt-content-reference{index="6"}

### 优缺点

优点是容易接入不同协议：只要适配器能给出输入对应的输出，就能参与搜索，不必先实现解析导数。

缺点是存在离散误差。例如真正最优比例可能是 63.7% / 36.3%，5% 网格无法表达；共享池处理也会让状态空间变复杂。

**对 Mantle，我建议把它用作初始解，再用连续优化精修，而不是长期停留在固定百分比枚举。**

## 3.3 边际价格均衡：同交易对多池拆单最值得优先实现的算法

这类方法最贴近你提到的“同交易对分散在不同协议”。

### 核心思想

不是看“哪个池子现在价格最好”，而是看：

> **再增加一小单位输入，放到哪个池子能够增加最多输出？**

假设有若干条互不共享池子的路径：

\[
\max \sum_i F_i(x_i)
\]

满足：

\[
\sum_i x_i=Q,\quad x_i\ge 0
\]

在报价函数递增、凹，且暂不考虑固定启用成本的条件下，最优解中那些已使用、且未触及容量上限的路径，应满足：

\[
F_i'(x_i)=\lambda
\]

也就是**边际输出相等**。

如果某条路径的边际输出更高，就应该把一点交易量从边际输出更低的路径挪过去，直到不能继续改善。

### 恒定乘积池可以直接求解

对前面的报价函数：

\[
f_i'(x)=
\frac{\gamma_i X_iY_i}{(X_i+\gamma_i x)^2}
\]

因此，给定一个目标边际价格 \(\lambda\)，可以得到：

\[
x_i(\lambda)
=
\max\left(
0,\,
\frac{\sqrt{\gamma_iX_iY_i/\lambda}-X_i}{\gamma_i}
\right)
\]

再对 \(\lambda\) 做二分搜索，使：

\[
\sum_i x_i(\lambda)=Q
\]

这就得到一个非常实用的同交易对拆单算法。

这里的公式是上述模型的直接推导；它不意味着所有协议都可以使用同一公式。

### 一个构造算例

假设两个 A/B 池，当前价格相同，手续费都为 0.3%：

| 池子 | A 储备 | B 储备 |
|---|---:|---:|
| 池一 | 1,000,000 | 1,000,000 |
| 池二 | 500,000 | 500,000 |

用户卖出 150,000 A。忽略 Gas 和整数取整：

| 方案 | 输入分配 | B 输出 |
|---|---|---:|
| 全部走池一 | 150,000 / 0 | 130,094.38 |
| 全部走池二 | 0 / 150,000 | 115,118.16 |
| 拆到两个池子 | 100,000 / 50,000 | **135,991.63** |

拆单比最佳单池方案多得到约 **4.53%**。

这个例子中恰好按储备比例拆分，是因为两个池子的初始价格、费率相同，曲线按规模成比例；**不能把这个结论推广成“所有池子按 TVL 比例拆单”。**

### 多跳也可以使用这个思想

如果一条路径由多个池子串联：

\[
F_p(x)=f_3(f_2(f_1(x)))
\]

其边际输出可通过链式法则计算。只要不同路径之间不存在共享池等耦合，就可以继续在路径级别做边际价格均衡。

### 可以借鉴谁？

Balancer SOR 的公开代码会计算交易后的路径价格及其导数，通过迭代调整交易量，使不同路径的边际价格接近，并考虑路径容量和执行成本。对应核心文件是 `src/router/sorClass.ts`。:chatgpt-content-reference{index="7"}

**这是我最建议你们优先吸收的拆单思想。**

## 3.4 增量流量分配：边搜索、边拆单

### 工作方式

把总输入分成多份，逐份分配：

```text
找到当前最优的增量路径
        ↓
分配一部分交易量
        ↓
更新相关池子的累计流量
        ↓
重新寻找下一部分交易量的最优路径
```

与“先找完所有路径，再决定比例”相比，它把路径发现和数量分配结合起来。

对于某个池子，若已经分配了 \(x\)，下一份输入为 \(\delta\)，在累计流量模型中，应比较：

\[
f(x+\delta)-f(x)
\]

而不是每次都把它当成一个全新的池子来计算 \(f(\delta)\)。

### 可以借鉴谁？

**Sushi Tines。**公开 SDK 中的 `Graph.ts` 会逐份调用寻路，再通过 `addPath` / `applySwap` 维护累计流量，最后生成执行步骤；`MultiRouter.ts` 还会比较单路径和多路径方案。:chatgpt-content-reference{index="8"}

**Jupiter Metis。**其公开技术说明将 Metis 描述为经过大幅修改的 Bellman–Ford 变体，采用增量构建、拆分和合并，并将路径生成与报价结合起来。这里应理解为针对交易路由设计的专用算法，而不是直接运行教科书中的 Bellman–Ford。:chatgpt-content-reference{index="9"}

### 适合什么场景？

适合需要更自然地处理复杂路径组合、共享中间资产和大规模候选图的场景。

但要注意：**在一般的共享池、固定 Gas、动态费率环境下，这仍然是启发式方法，不能仅凭“每一步都选最好”就宣称全局最优。**

对 Mantle，我会把它作为增强型引擎，与前面的“路径搜索 + 连续拆单”方案做对照，而不是直接假设它一定更优。

## 3.5 CFMM 凸优化：从整个池子网络联合求解

这是数学上最完整、也最值得作为质量基准的一类方案。

### 核心区别

前面几种方法倾向于先找路径，再给路径分量。

CFMM 优化则直接问：

> **每个池子应该收到哪些资产、交出哪些资产，才能满足整体资产守恒，并使目标资产输出最大？**

使用池级交易变量，而不是把每条路径视为独立流动性，可以自然表达多跳、拆分和共享池。

### 理论结果是什么？

Angeris、Evans、Chitra、Boyd 的《Optimal Routing for Constant Function Market Makers》证明：在论文的 CFMM 模型和假设下，**忽略固定执行成本时，最优路由可以写成凸优化问题；加入固定成本后，则变成混合整数凸优化问题**。:chatgpt-content-reference{index="10"}

一个直观表达是：

\[
\max \Psi_{\text{目标资产}}
\]

满足：

\[
\Psi=\sum_i A_i(\Lambda_i-\Delta_i)
\]

以及每个池子的合法交易约束、输入总量约束和中间资产守恒约束。

其中，\(\Delta_i\) 是给池子的资产，\(\Lambda_i\) 是从池子取出的资产，\(A_i\) 把池内资产映射到全局资产空间。

### 对偶分解如何加速？

后续论文《An Efficient Algorithm for Optimal Routing Through Constant Function Market Makers》提出了分解算法，并讨论了 Uniswap V3 这类聚合 CFMM。对应公开实现是 `bcc-research/CFMMRouter.jl`。:chatgpt-content-reference{index="11"}

可以把它理解为：先给每种资产设置一个内部估值，各个池子在这个估值下独立求解，然后根据全局资产供需偏差调整估值，重复直到协调一致。公开实现使用 L-BFGS-B 优化对偶问题。:chatgpt-content-reference{index="12"}

### 对你们有什么价值？

我认为有两个用途：

**第一，作为离线质量基准。**检查线上启发式 Router 是否遗漏了明显更优的流量分配。

**第二，作为全图增强引擎的候选。**你们提供的池子规模不大，值得实测，而不应先入为主地认定“全图优化一定太慢”。

但它不是可以无条件直接上线的完整 Router：

- 数学模型要与真实协议一致，任意动态费率、Hooks 或转账税不自动满足凸性假设。
- 求出的池级交易集合，还需要转成资金可达、顺序正确的执行计划。
- 固定调用成本、整数取整和真实 Gas 必须另行处理。

CFMMRouter 的文档也明确区分了“无序交易集合”和“可执行交易序列”，并提示非严格凹、例如恒定和模型下的可行解恢复问题。:chatgpt-content-reference{index="13"}

**尤其对 Liquidity Book，不能只看到“也是集中流动性”就默认现成求解器可以直接套用。**

## 3.6 分段线性近似：适合深度分段与复杂流动性

这是一种可组合的建模方式，不必单独成为一套产品。

思路是把报价曲线近似成若干深度段：

```text
前一段输入：边际兑换率较好
下一段输入：边际兑换率略差
再下一段：继续变差
```

每一段有自己的容量和兑换关系，再使用线性规划；如果包含启用固定成本、不可部分成交的报价等离散条件，可以增加整数变量。

对于已经确认凹性的报价函数，还可以利用弦线和切线构造保守近似及上界，辅助控制求解误差。

**注意，它不是普通的最小费用流原样套用。**不同边两端是不同资产、兑换率不同，而且同一个物理池的不同方向或不同交易对可能共享状态，必须保留这种关联。

我建议在以下情况下使用它：解析导数难实现、报价函数有明显深度分段，或者未来要把 AMM 与订单簿、RFQ 放到同一个优化框架里。最终结果仍要用原始协议数学重新计算。

# 四、最容易做错的地方：共享池不能重复计算

这一点值得单独强调，因为它会直接导致“报价很好，但执行不出来”。

## 4.1 错误发生在哪里？

假设两个路径：

```text
路径一：A → 池一 → C → 池三 → B
路径二：A → 池二 → C → 池三 → B
```

两条路径共享池三。

如果分别按池三的初始状态计算：

\[
F_1(x_1)+F_2(x_2)
\]

就相当于把池三的初始流动性使用了两遍。

正确做法可以是：把前两条分支产生的 C 合并，然后计算：

\[
f_3\left(f_1(x_1)+f_2(x_2)\right)
\]

也可以按实际调用顺序逐步更新状态模拟；但**不能独立报价后直接相加**。

## 4.2 一个能看出误差大小的算例

假设三池手续费均为 0.3%：

| 池子 | 储备 |
|---|---|
| 池一 A/C | 1,000,000 A + 1,000 C |
| 池二 A/C | 500,000 A + 500 C |
| 池三 C/B | 1,000 C + 1,000,000 B |

将 150,000 A 分为 100,000 A 和 50,000 A，前两池分别产生约 90.6611 C 和 45.3305 C。

接下来：

| 计算方式 | 最终 B 输出 |
|---|---:|
| 错误：两份 C 分别使用池三初始状态报价，再相加 | 126,136.52 |
| 正确：合并 C 后，通过池三兑换 | **119,395.57** |

错误算法高估约 **5.65%**。

这不是优化收益，而是重复使用流动性造成的虚假报价。

## 4.3 三种处理策略

| 策略 | 好处 | 代价 |
|---|---|---|
| 禁止拆分路径共享池子 | 简单，适合可靠基线 | 会丢掉一部分更优交易结构 |
| 按统一状态顺序模拟 | 能正确处理状态依赖 | 路径间耦合更强，搜索更复杂 |
| 池级流量优化，再合并为执行图 | 能表达共享前缀、后缀及中间合流 | 需要执行图编译和完整模拟 |

Uniswap 公开 SOR 选择了第一类限制；1inch 的 Pathfinder 升级则展示了第三类结构优化的产品价值。两者不是谁“支持拆单”谁“不支持拆单”，而是**允许表达的交易结构不同**。:chatgpt-content-reference{index="14"}

对于 Mantle，我建议：**第一类做基线，但数据结构从一开始就为第三类预留空间。**

# 六、结合 Mantle，我建议怎样设计？

## 6.1 最先做好的不是搜索，而是统一报价适配层

你的问题里有“不同协议的同交易对”，所以不能默认所有池子都能套用同一个公式。

例如，Agni 的官方生态介绍采用集中流动性设计；Merchant Moe 的 Liquidity Book 则使用 bins、恒定和区间和固定加可变费率，与 Uniswap V3 并不相同。:chatgpt-content-reference{index="30"}

建议把每类流动性来源抽象为：

```text
读取指定区块的状态
给定输入量，计算输出
返回或应用交易后的状态
估算执行成本
查询容量、价格区间和特殊限制
构建可执行调用
```

如果模型支持，再提供边际价格或导数接口。

这与 KyberSwap DexLib 将池发现、状态跟踪和模拟拆分的思路接近。:chatgpt-content-reference{index="31"}

**报价层不准确时，把拆单精度从 5% 提升到 0.1%，只是在更精细地优化错误数据。**

## 6.2 100 多个池子的优势：可以更完整地维护状态

基于你给出的规模，我建议优先采用：

**完整池图常驻内存，按新区块和事件更新状态；每笔请求只在相关子图上计算。**

相比一开始就做大量近似索引，这样更利于排查问题和验证正确性。

但“100 多个池子”不等于“只有 100 多个报价状态”。集中流动性池还涉及 ticks，Liquidity Book 涉及 bins，查询和模拟成本必须实测。

## 6.3 推荐的端到端流水线

```text
确定输入、输出、金额及报价区块
                ↓
取得一致的池状态快照
                ↓
生成直接、两跳、三跳候选
                ↓
在多个交易规模上报价，筛选候选
                ↓
离散组合搜索，得到初始拆单方案
                ↓
连续优化拆单比例
                ↓
识别共享池，合并并重新优化
                ↓
生成执行图及 calldata
                ↓
完整交易模拟、实际费用估算
                ↓
比较净输出，返回最佳可执行方案
```

这里，“合并共享池”不能只是最后做一次结构美化：合并会改变报价曲线和 Gas，必要时需要回到优化步骤重新分配交易量。

## 6.4 初始参数建议

以下是开发起点，不是回测结论：

| 参数 | 建议起点 |
|---|---|
| 交易类型 | 优先 Exact Input |
| 最大跳数 | 3 |
| 初始最大拆分路径数 | 4 |
| 最终使用的独立池数量 | 先设 6–8 的软限制，按净收益和执行预算调整 |
| 初始拆分粒度 | 5%，然后连续精修或局部细化 |
| 最终完整模拟 | 对若干个高分候选统一模拟 |
| 小额交易 | 必须保留最佳单路径方案作为候选 |
| 共享池暂未支持时 | 明确禁止，不能独立报价后相加 |

小额交易和大额交易不必采用完全相同的搜索预算。建议以交易价值和潜在改善空间决定是否扩大搜索，而不是让每笔小单都进行最复杂的求解。

## 6.5 Gas 优化应该放在两个位置

**搜索时做近似，最终选优时做完整估算。**

搜索时，可以使用每类池子的基础成本、跳数、预计跨越区间等特征。

最终阶段，应对完整执行计划估算成本，因为共享步骤合并、资产转移方式、包装与解包、合约调用结构都会影响结果。Balancer 的公开算法就有“增加路径后比较扣费收益，改善停止则停止扩展”的设计。:chatgpt-content-reference{index="32"}

对 Mantle，费用模型应该接入目标网络当前实际的估算规则，避免照搬其他链参数，也避免把已经包含的费用再次相加。

# 七、怎么判断“尽可能最优”真的做到了？

我建议不要直接用“多跳和拆单上线了”作为验收标准，而是建立可重复的分层对照。

## 7.1 做六组消融比较

| 组别 | 允许的能力 | 衡量的收益 |
|---|---|---|
| A | 最佳直接单池 | 基线 |
| B | 最佳单路径，可多跳 | 多跳的独立贡献 |
| C | 直接交易对之间拆单 | 同交易对流动性聚合的贡献 |
| D | 多跳 + 不共享池的拆单 | 基础智能路由贡献 |
| E | 支持共享池及合流 | 执行图优化贡献 |
| F | 更大搜索预算或模型求解器 | 检查线上方案遗漏的机会 |

这能回答一个很重要的问题：

> **Mantle 上的收益究竟主要来自多跳、同交易对拆单，还是共享中间流动性？**

这三者的开发成本不同，应由实际数据决定后续投入。

## 7.2 严格区分三种比较

**算法比较：**使用同一个区块、相同池集合、相同手续费和 Gas 假设。

**完整交易比较：**比较实际 calldata 模拟后的输出、费用和可执行性。

**外部聚合器比较：**如果对方 API 无法固定区块，或者使用你们尚未接入的 RFQ，那么它只能作为近实时产品对照，不能直接当成严格的算法最优性证明。

另外，无 Gas 的凸优化结果，不能未经调整就与包含 Gas 的线上净输出计算“最优差距”；必须统一目标函数和约束。

## 7.3 建议跟踪的指标

| 指标 | 需要回答的问题 |
|---|---|
| 相对最佳单池、最佳单路径的净改善 | 复杂路由是否真的值得 |
| 相对高预算基准的差距 | 线上搜索遗漏了多少 |
| 报价与同状态模拟的误差 | 协议数学和执行编译是否一致 |
| 报价延迟及尾延迟 | 增加搜索预算是否影响体验 |
| 模拟失败、实际回退及重报价比例 | 方案是否可靠 |
| 跳数、拆分数、独立池数量 | 收益是否来自过度复杂的路线 |

尤其应该把**整数取整、共享池、跨 tick/bin、动态费率、极低流动性、转账税代币**列为专门的测试类别，而不是仅用主流交易对的正常状态做验证。

# 八、最终选型建议

如果这是 Mantle Router 的自建项目，我会这样安排：

| 阶段 | 核心内容 | 借鉴对象 |
|---|---|---|
| **可靠基线** | 统一池适配器、有限跳数搜索、离散拆单、完整交易模拟；暂时排除共享池冲突 | Uniswap SOR、KyberSwap DexLib |
| **主要优化** | 连续拆单、共享池流量计算、拆分合流、真实 Gas 反馈 | Balancer SOR、Sushi Tines、1inch 的结构设计 |
| **质量上限研究** | 全图 CFMM 求解、分段模型、与线上结果持续对照 | CFMMRouter.jl 及相关论文 |

离线基准可以从第一阶段就并行建立，但我不建议把包含所有真实执行细节的混合整数求解器，直接作为首版每笔请求的必经路径。

还有一点：**这些能力首先是 Router 中间件和执行合约能力，不需要为了实现多跳、拆单而改造账户模型或引入新的链级指令。**链侧更值得配合的是状态获取、模拟能力、费用估算和交易提交质量。Jupiter 最近公开的升级也在强调状态新鲜度、执行风险和临近执行时的路由决策，说明“静态报价最优”之外仍有一层独立的执行优化问题。:chatgpt-content-reference{index="33"}

**归纳到你们当前的需求，我的优先级是：先把所有相关池子准确地“算对”，再用边际价格把交易量“分对”，最后把共享池和执行步骤“合对”。**

对于同交易对流动性明显分散的 Mantle 场景，这比单纯提高最大跳数，或者只把拆单百分比切得更细，更有希望形成持续、可验证的报价优势。
